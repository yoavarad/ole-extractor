## AI Analysis
### Patterns
- Sprint 301 was one coherent epic, per-field error isolation: a primitive first (303 FieldError DTO + leaf-isolation primitive), then rollout per area, then guards.
- Rollout followed a repeated per-handler shape: property isolation (304), Word/Excel (307), PowerPoint (308), flat-text (309), subfile isolation (310). Each applied the same leaf-isolation primitive to a different surface.
- Console swallows were removed as part of the isolation work (308, 310), so isolation replaced silent error hiding with reported FieldErrors.
- Adversarial fixtures were authored in their own tasks (305 docx, 306 legacy) before or alongside the handler work, so the isolation behavior had concrete corrupt inputs to test against.
- The sprint ended with regression guards and manifest-driven checks (311 fatal set still throws, field-errors-only is a batch success; 312 expectedFieldErrors per manifest entry and a zero-FieldErrors corpus regression), which lock in the contract.
- Open/populate splits (307) and keying isolation by package path (310) show the design needed structural changes to give failures a precise location, not only try/catch wrapping.
- Task ordering was dependency-driven: DTO and primitive, then fixtures and handlers, then guards. Handler tasks were granular enough to be completed independently.

### Template suggestions
- Handler leaf-isolation task template: list the format's leaves, wrap each in the isolation primitive, report failures as FieldErrors with a field path, remove Console swallows, and name the adversarial fixture that exercises it.
- Adversarial fixture task template: fixture name, corruption mechanism, expected FieldError path/code, expected unaffected fields, and the manifest expectedFieldErrors entry.
- Regression guard task template: invariant statement (for example fatal set throws with no result; field-errors-only is a batch success), the test that proves it, and the corpus-level zero-FieldErrors check.
- Epic skeleton template: primitive/DTO task, then fixtures, then per-handler rollout tasks, then guard and manifest tasks.

### Rule suggestions
- No Console.* swallowing of exceptions in extraction code. Failures must surface as FieldErrors or throw as part of the fatal set.
- Every new isolated leaf must have an adversarial fixture and a manifest expectedFieldErrors entry.
- Isolation failures must be reported at the most specific location available (field path or package path), not at a parent aggregate.
- Keep the fatal-versus-field-error boundary explicit: fatal failures throw with no partial result, and field-error-only outcomes count as batch success. Guard this with a test whenever isolation scope changes.
- Introduce shared primitives and DTOs in a dedicated early task before handler rollout tasks begin.
- Corpus regression must assert zero FieldErrors on known-good files so isolation never masks real failures.

### Summary
Sprint 301 delivered the per-field error isolation epic across 10 tasks (303-312). It added the FieldError DTO and leaf-isolation primitive, isolated the 12 FileMetadata properties, and rolled isolation out to Word, Excel, PowerPoint, flat text and subfiles while removing Console swallows. It authored adversarial fixtures for docx and legacy formats, and closed with regression guards and a manifest-driven corpus check. The primitive-first, rollout-per-handler, guards-last structure worked well and is worth templating.

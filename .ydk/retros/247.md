### Template suggestions
- Ported-review-finding template: source repo and comment link, current-state check (what already exists, with task or ADR references), remaining gap, scope, acceptance criteria, and a sentence on why it still applies to this codebase.
- God-class split checklist: list responsibilities, target classes and interfaces, DI registration changes, what stays as a thin facade, callers to migrate, and focused unit tests per new class.
- Public API change template: new or removed signatures, DI ambiguity check for added constructors, default-behaviour-unchanged test, and a migration note for external consumers.
- Folder or namespace restructure template: file move list, confirmation that removed types have no references (grep), namespaces matching folders, and a requirement that it runs after any dependent refactor.

### Rule suggestions
- Before starting a ported review task, verify the current state of the code and trim the scope to the remaining gap, recording what is already done with references.
- When adding a constructor overload to a type resolved by DI, add a test or note covering direct container registration, since multiple constructors can become ambiguous.
- Open reviewer findings must be converted into a follow-up task or an explicit won't-fix note before the PR merges, not left as an unresolved comment.
- Deleting code (such as Old/ or a library-level Program.cs) requires a recorded reference check (grep or graphify) in the PR description.
- Structural moves and renames should be sequenced after the refactors they depend on, with the dependency declared on the task.
- Public API removals or signature changes must be documented repo-wide (changelog or ADR) in the same PR.

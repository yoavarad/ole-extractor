### Template suggestions
- CI Build Break Template: Title: Fix [Tool/Library] [ErrorCode] in [Component] | Fields: Affected component, Error code or warning, Root cause (e.g., obsolete API), Fix applied, Regression test added (Y/N), Time to resolution | Use when: Any CI pipeline failure is introduced by dependency changes or deprecated APIs
- Tooling Migration Template: Title: Migrate [Process/Tool] to [New Platform] | Fields: Current tool/process, Target tool/process, Migration steps, Data or history preserved (Y/N), Team communication plan, Rollback plan, Completion criteria | Use when: Adopting a new platform or workflow for an existing process
- Technical Debt Task Template: Title: Resolve [Debt Type] in [Module/Component] | Fields: Origin of debt, Business impact if unresolved, Estimated effort, Dependencies or blockers, Definition of done | Use when: Proactively scheduling known legacy issues before they cause breakage

### Rule suggestions
- Rule 1 - CI Hygiene: Any compiler warning flagged as CS0618 (obsolete API usage) must be resolved within the same sprint it is detected, preventing accumulation of suppressed warnings that become build breaks
- Rule 2 - Reactive Task Cap: No more than 1 unplanned reactive task (e.g., build fixes, hotfixes) should consume sprint capacity without a corresponding sprint scope adjustment or stakeholder notification
- Rule 3 - Migration Definition of Done: All tooling or process migration tasks must include a documented cutover checklist and a grace period where both old and new systems are verified before the old one is retired
- Rule 4 - Capacity Transparency: Sprints with fewer than 3 completed tasks should trigger a brief capacity retrospective note to distinguish between low-load planning, unplanned interruptions, or estimation issues
- Rule 5 - Obsolete Dependency Tracking: A recurring backlog item should exist to audit third-party library usages (e.g., NPOI) for deprecated APIs at least once per quarter to prevent reactive CI breaks

## Description

Discovered while unblocking T-b62ffe04: its acceptance criteria require a fixed 10MB and a fixed ~100MB sample for each of the 6 formats (docx, xlsx, pptx, xls, doc, ppt = 12 files), but `samples/` has nothing at those sizes (largest committed sample is the 6.8MB curated pptx; `samples/synthetic/large-body/*` are 13-19KB) and `ExtractorOle/ExtractorOLE.Benchmarks/ExtractionBenchmarks.cs` is a 49-line single-docx stub. This task produces only the inputs; the benchmark wiring stays in T-b62ffe04.

Conventions to follow:
- Generation lives in `SampleGenerator/` (deterministic: no RNG, fixed inputs such as `MultilingualFixtures.ComposeLargeBody`), and every sample is recorded in `samples/manifest.json` (format, generatedBy, compositionRule, size) as the existing entries are.
- Every committed sample today is <= 6.8MB. Twelve files of 10MB-100MB (~600MB for the 100MB tier alone) must NOT be committed: write them to a gitignored directory (`samples/benchmark/`), regenerate on demand, and record a SHA-256 per file in the manifest so a regeneration can be checked byte-for-byte.

Size/validity constraints that come from the guardrails (do not skip):
- `MimeDetectionLimits.MaxFileSizeBytes` = 104,857,600 (100 MiB) and the check is strictly `>`; the ~100MB tier must be <= 104,857,600 bytes or it hits file-too-large (already enforced in the mime detectors, and being added to Extract() by T-3335d397).
- `MaxDeclaredNestedContentBytes` = 2 GiB of declared uncompressed OOXML entry sizes; padding a docx/xlsx/pptx with highly compressible filler could trip oversized-nested-content. Use realistic, low-compressibility content so the 100MB files stay well under the declared-size cap.
- Samples must contain real extractable content in every format (legacy doc/xls/ppt included), so the benchmark times real extraction and not a no-op/failure path.

## Description

Follow-up from the corpus integration test (PR #120, ExtractorOle/ExtractorOLE.Tests/Integration/ExtractCorpusManifestTests.cs, not yet merged when this task was filed). For the two curated third-party pptx samples the manifest count and the real extractor count disagree. samples/manifest.json expectedSubfileCount is 58 for samples/curated/pptx/noaa-transition-team-briefing-2008.pptx and 83 for samples/curated/pptx/ornl-quasi-elastic-neutron-scattering-introduction.pptx, but MainExtractor.Extract returns 59 (NOAA) and 58 (ORNL) subfiles. The manifest numbers are raw counts of package parts under ppt/media/ (and ppt/embeddings/ for ORNL), and the manifest notes say the extractor's naming/ordering was never run against these files (detectable=false pending that verification). The extractor (ExtractorOle/ExtractorOLE/Helpers/ExtractionHelper.cs, ExtractFirstLayerEmbedded) instead counts every image and OLE relationship hosted by a level-1 part (slides, layouts, masters), so a part shared by several slides is counted once per relationship, i.e. twice or more. The integration test currently pins the extractor's numbers via a documented override instead of the manifest values. Decide which side is right per docs/specs/extraction.md (Subfiles - one entry per first-layer OLE-embedded object and inline media item) and the subfile-scope requirement (.ydk/components/req/extraction/subfile-scope.yaml), which speaks of parts, not relationships. Then either fix the extractor (for example dedupe shared parts by part URI so each media/embedding part is listed once) or correct the manifest counts, record the reasoning in the manifest notes, and remove the override from the test.

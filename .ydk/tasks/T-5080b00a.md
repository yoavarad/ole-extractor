## Description

Bug. ExtractorOle/ExtractorOLE.Tests/StressHarness/LoadGeneratorTests.cs RunAsync_Concurrency500_ReachesPeakObservedConcurrencyOf500 (exercising ExtractorOle/ExtractorOLE.StressHarness/LoadGenerator.cs) is flaky under machine load. It runs LoadGenerator.RunAsync with Concurrency 500 and Iterations 1000 and an operation of Thread.Sleep(200), then asserts PeakObservedConcurrency == 500. Under CPU contention it observed a peak of 494. It passes when run alone (7/7 in the class). It failed the dotnet test gate in PRs #118, #119 and #120 while several agents ran in parallel, and failed at least one ydk task done verification run. Suspected root cause (to confirm and document): the assertion depends on wall-clock timing. The 500 operations must all be in flight within the same 200 ms sleep window; when the ThreadPool (even with SetMinThreads and a warm-up) or the scheduler is starved, early operations finish before the last ones start, so the in-flight counter never reaches 500. Fix it by removing the timing dependency, for example make the test operation block on a gate/barrier (CountdownEvent or Barrier with 500 participants, or a ManualResetEventSlim released once 500 callers have arrived, with a generous timeout so a real failure fails instead of hanging) so that peak concurrency 500 is reached deterministically, and/or expose a controllable clock or hook in LoadGenerator. Do not add retries and do not lower the asserted 500.


## Activity Log

- 2026-09-25: Root cause confirmed. `LoadGenerator.RunAsync` already tracked
  peak concurrency correctly via `Interlocked.Increment`/`UpdatePeak`
  immediately before invoking the operation and `Interlocked.Decrement`
  immediately after it returns (not periodic sampling). The flakiness came
  from the *test*: it used `Thread.Sleep(200)` as a proxy for "long enough
  that all 500 callers overlap." Under CPU contention the ThreadPool/OS
  scheduler could take longer than 200ms to get all 500 worker threads
  actually running, so earlier callers finished (decremented in-flight) and
  freed a semaphore slot before the last callers ever started -- so peak
  never reached 500 (observed 494/357/287 under load).
  Fix: replaced the sleep with a `Barrier(500)` in
  `RunAsync_Concurrency500_ReachesPeakObservedConcurrencyOf500`
  (`ExtractorOle/ExtractorOLE.Tests/StressHarness/LoadGeneratorTests.cs`).
  Because `LoadGenerator` only decrements a call's in-flight count *after*
  the operation returns, and a `Barrier` cannot release any of its 500
  participants until all 500 have signaled, no call can free a concurrency
  slot until every one of the 500 concurrent callers has already been
  counted toward the peak -- making peak==500 deterministic regardless of
  scheduling speed. A 30s bounded timeout on `Barrier.SignalAndWait` fails
  the test with a clear `TimeoutException` message instead of hanging if
  fewer than 500 callers ever run concurrently. No retries added, assertion
  unchanged (`Assert.Equal(500, ...)`).
  Verified: 20/20 parallel `dotnet vstest` runs of this test passed while 20
  CPU busy-loop stress processes were running concurrently on a 22-core
  machine. Full `dotnet test` suite: 379 passed, 0 failed, 1 pre-existing
  skip (unrelated).

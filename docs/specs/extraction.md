# Extraction

## Purpose

[ydk:contract:extraction/extract] turns a file already classified by mime detection into a full result: general metadata, format-specific metadata, flat text, and first-layer subfiles. It trusts the caller-supplied detected format rather than re-detecting — detection and extraction are separate, sequential steps by design.

## General Metadata

[ydk:entity:extraction/FileMetadata] carries the fields common across all six formats — title, author, last-modified-by, subject, keywords, comments, created/modified timestamps, application name, revision number, cumulative editing duration, and last-printed timestamp — sourced from each format's native document-properties store. A field the source format doesn't provide is null, never a placeholder string.

Implementation naming: the C# `FileMetadata` DTO uses `Creator` (entity `Author`), `Created` (entity `CreatedAt`), `Modified` (entity `ModifiedAt`) and `LastPrinted` (entity `LastPrintedAt`); the other fields keep the entity names, and `EditingDurationMinutes` is whole minutes for both OLE EditTime and OOXML TotalTime. The sample manifest uses the entity name `Author` and maps it to `Creator`. On the result itself the C# names are `Metadata` (entity `GeneralMetadata`) and `EmbeddedFiles` (entity `Subfiles`). A [ydk:entity:extraction/FieldError] field path is spelled with the C# names, never the entity names, and this is deliberate: the path has to match character-for-character the property the caller just read as null, or every caller has to translate the spec's vocabulary into its own compile-time surface before it can act on an error. The entity names remain this spec's own vocabulary for describing the model, so the three that differ never appear in a path — `GeneralMetadata` is `Metadata`, `Subfiles` is `EmbeddedFiles`, `CreatedAt` is `Created`, and likewise `Author`, `ModifiedAt` and `LastPrintedAt` are `Creator`, `Modified` and `LastPrinted`.

## Format-Specific Metadata

Exactly one metadata shape populates the result, chosen by format kind (Word, Excel, or PowerPoint — distinct from format family, which is the container technology; see `glossary.md`):

- [ydk:entity:extraction/WordFormatMetadata] — doc/docx (page/word/character/paragraph counts, company/manager/template fields, macro-presence flag)
- [ydk:entity:extraction/ExcelFormatMetadata] — xls/xlsx (sheet count/names, active sheet, macro-presence flag)
- [ydk:entity:extraction/PowerPointFormatMetadata] — ppt/pptx (slide count, notes-slide count, macro-presence flag)

This is a discriminated union at the API level, not a bag of nullable fields for every format on one type. Every format kind carries its own macro-presence flag (see `mime-detection.md` for why detection itself doesn't split macro variants into separate detected formats).

## Flat Text

The flattened plain-text body is empty, never null, when there's nothing to extract — and also when flattening failed, which is why the empty string alone is not an answer: the two cases are told apart by whether the result carries a [ydk:entity:extraction/FieldError] for the text (see Per-Field Error Isolation), not by inspecting the string. Must satisfy [ydk:req:extraction/unicode-fidelity]: Hebrew, Arabic, Persian, Russian, Latin, and CJK text, plus emoji (including multi-codepoint sequences), must round-trip without mojibake or truncation. This is explicitly harder on the legacy path (per the library research spike, exact text-decoding behavior for mixed-encoding legacy fields is unverified) than the OOXML path (already Unicode-native internally) — empirical testing against the multilingual corpus is required before this requirement is considered met for legacy formats.

## Subfiles

The subfiles list holds one entry per first-layer OLE-embedded object and inline media item, per [ydk:req:extraction/subfile-scope] — binary, filename, and size for each. Internal package structure that isn't an embedding or media item (the exhaustive exclusion list is in [ydk:req:extraction/subfile-scope]) is never listed as a subfile. A subfile that is itself a container (e.g. an embedded spreadsheet inside a document) is returned as one opaque item — its own contents are not recursively unpacked in v1.

OOXML (docx/xlsx/pptx and macro variants) subfile `FileName` is `<prefix>_<N><ext>`, where `<N>` is the 1-based position in the returned list and `<ext>` the item's file extension: the prefix is `slide_image` for an image part hosted one hop below the main part (a slide or worksheet, in pptx and xlsx) and `embedded_object` for every other item (OLE/package embeddings at any level, and image parts related directly to the main part, as in docx) — the prefix follows where the part sits in the package, not the document kind, so an xlsx image is `slide_image_N`; `samples/manifest.json` records these exact names.

**Counting rule.** A subfile is a distinct package part (OOXML) or top-level/pool storage or picture record (legacy), not a relationship, so the subfile count is not always the literal number of embeddings a sample was authored with. Any embedding or media part reachable from the main part counts exactly once, wherever it is hosted (slide, worksheet, layout, master, or OLE-preview/vmlDrawing image; a part shared by several hosts is listed once, per PR #125), but the enumeration never descends into a subfile's own contents. Consequences recorded in `samples/manifest.json`: (a) the OLE-preview icon picture that a legacy xls object needs is itself a picture and counts, so `multi-embedding/sample.xls` returns 5 subfiles for 4 authored embeddings; (b) the placeholder VBA project of OOXML macro variants (docm/xlsm/pptm) and of legacy doc/xls is a macro flag, not a subfile, whereas legacy ppt reports every top-level storage as an embedded object, so `macro-embed/sample.ppt` returns 2 (Embedding1 plus the Macros storage). (b) is a known legacy-ppt asymmetry, accepted and recorded rather than special-cased; the manifest `expectedSubfileCount` for every sample follows this rule rather than the authored embedding count.

If an individual embedded item cannot be read (its own bytes are corrupt while the surrounding document is fine), it is omitted from the subfiles list and the omission is reported as a [ydk:entity:extraction/FieldError] keyed by that item's own package path — not merely logged — and this does not fail the overall extraction call. A single bad embedding shouldn't deny access to an otherwise-good document, but a caller still has to be able to tell that the list it received is shorter than the document's, which a log line it never sees cannot do. The counting rule above describes the document; the returned list describes what was readable, and the gap between the two is exactly what the field-error entries account for.

## Error Handling

Extraction fails the whole call for the fixed set below and for nothing else. The set is enumerated rather than characterised, because no single test produces it: argument validation runs before a byte is read, unsupported-format is decided from the supplied detected-format value alone, and the remainder are failures of the container open itself. What the members share is the outcome, not the mechanism — in each case nothing is extractable, so a partial result would say only that the file was unreadable, which is what the thrown error already says, more precisely.

- [ydk:error:extraction/file-too-large] — rejected before parsing
- [ydk:error:extraction/password-protected] — encrypted content detected before a full parse is attempted
- [ydk:error:extraction/unsupported-format] — the supplied detected-format value isn't one of the six supported formats
- [ydk:error:extraction/truncated-container] — declared container size exceeds actual byte length, or the input is zero-length
- [ydk:error:extraction/corrupt-file] — in its container-level role only: the container's own structure is unparseable, so no document is ever opened
- [ydk:error:extraction/oversized-nested-content] — in its open-time role only: a [ydk:nfr:extraction/nesting-depth-guard] cap is breached by the container's own declared structure, while the container is still being opened

A null request object, or a null value on a required request field, is rejected immediately via standard argument validation before any of the above logic runs — this is boundary validation, not a domain error, and has no dedicated error manifest. An exception no component declared, raised while the container is still being opened, is fatal on the same grounds and propagates unwrapped exactly as raised: it is not translated into one of the errors above, and no [ydk:entity:extraction/FieldError] is possible for it because there is no result object yet to carry one. Both are the same convention as ADR-009's argument validation — the boundary throws what it has, and the per-field channel exists only for the interval in which a result does.

Every failure after the container opens is isolated to the leaf it affects and reported through the per-field channel below instead of being thrown. Two of the errors above therefore carry two roles each, and in both cases the dividing line is the same single question — had the container finished opening? — not the exception's type, not the backing library that raised it, not how deep in the document the bad record sits. For [ydk:error:extraction/corrupt-file], unparseable container structure is fatal and an unparseable source record behind one leaf is not. For [ydk:error:extraction/oversized-nested-content], a guard breach detected during the open is fatal, because what breached the cap is the container's own declared structure and there is no result to attach a field error to; a breach detected on one leaf after a successful open costs the caller that one item and nothing else. The [ydk:nfr:extraction/nesting-depth-guard] caps themselves are unchanged in both roles — hard ceilings, enforced before any buffer is allocated. The error stays wholly fatal on [ydk:contract:extraction/detect-mime-type], which produces a single verdict and has no per-field channel to report into.

## Per-Field Error Isolation

[ydk:req:extraction/per-field-error-isolation] makes the leaf property the unit of failure — not the result, and not an output group. Each of the twelve source-derived properties on [ydk:entity:extraction/FileMetadata], each leaf property of whichever format-metadata shape applies ([ydk:entity:extraction/WordFormatMetadata], [ydk:entity:extraction/ExcelFormatMetadata], [ydk:entity:extraction/PowerPointFormatMetadata]), the flat text, and each individual subfile ([ydk:entity:extraction/SubfileItem]) succeed or fail independently of every other one. A document whose creation timestamp is stored in a mangled property-store record still yields its title, its author, its word count, its body text, and its embeddings; the caller loses one timestamp.

A failed leaf is left at its no-value state and is never given a placeholder, a sentinel, or a guess: a nullable property is null, the flat text is the empty string, a failed subfile is absent from the list. The non-nullable counts and flags — the Excel sheet count and sheet names, the PowerPoint slide count, every format kind's macro-presence flag — carry their type's default when they fail, meaning zero, false, or an empty list, and that default is explicitly *not* a claim about the document. A caller cannot distinguish "this workbook genuinely has no macros" from "we could not determine whether it has macros" by reading the flag, and must not try: the [ydk:entity:extraction/FieldError] entry for that leaf's path is the only discriminator, in both directions. No entry means the value is the document's; an entry means the value is a placeholder the caller should treat as unknown. This is deliberate — widening those leaves to nullable would change the result shape every existing caller already compiles against, for a signal the field-error collection carries anyway.

A defaulted leaf is also not reconciled against its siblings. An Excel sheet count of 0 sitting next to a populated list of sheet names is the expected shape of one failed leaf beside a succeeding one: the count is not quietly recomputed from the names, and the names are not cleared to match the count. Either repair would put a guess on the public surface, which is the one thing this rule forbids. The inconsistency is the honest report of what was readable, and the field-error entry for the failed leaf is what explains it; a caller that trips over the pair must resolve it by reading the collection, not by picking whichever value looks more plausible.

Three required properties on [ydk:entity:extraction/FileMetadata] sit outside the isolated set altogether: `FileSizeBytes`, `ExactMimeType` and `FormatFamily`. None of them is read from a parsed source record — they derive from the request and from the detection verdict the caller supplied with it — so once the container has opened they are already known and have no way to fail. The twelve source-derived properties are the whole of the general-metadata isolation surface, and these three never appear in a field path.

[ydk:entity:extraction/FieldError] is additive: a new collection on [ydk:entity:extraction/ExtractionResult] carrying a field path, an error code from a closed three-value vocabulary, and a human-readable message. Nothing existing changes type, so a caller that ignores the collection sees exactly the result it saw before, with the pre-change behavior it already handles. The originating exception is deliberately not on the public surface — code and message only, with the exception type and stack going to the log/telemetry sink, so the public result never pins callers to a backing library's exception taxonomy.

Which of the three codes a failed leaf carries is decided by the cause, not by the leaf: the source record behind that leaf is unreadable or malformed → CORRUPT_FILE; the leaf is an item that breached a [ydk:nfr:extraction/nesting-depth-guard] cap → OVERSIZED_NESTED_CONTENT; anything else → UNEXPECTED_FIELD_FAILURE. The third is the residual bucket for a failure mode this spec did not anticipate, so it is never used where either of the first two fits, and reaching for it on a cause that recurs is the signal that the vocabulary needs a fourth value and a spec change rather than a looser third. The vocabulary is only partly shared with the thrown errors: CORRUPT_FILE and OVERSIZED_NESTED_CONTENT are the codes of [ydk:error:extraction/corrupt-file] and [ydk:error:extraction/oversized-nested-content] in their field-level roles, so a caller handling both channels sees the same two names in each, while UNEXPECTED_FIELD_FAILURE has no error manifest and is never thrown out of the call at all.

The field path is a dotted path rooted at the result and spelled with the result's own public C# property names, never the entity names (see the naming bridge above): `Metadata.Created` or `Metadata.Title` for a general-metadata property, `FormatMetadata.PageCount` for a format-metadata property, `ExtractedText` for the flat text. A failed embedded item is keyed by its package path rather than by any number — `EmbeddedFiles[word/embeddings/oleObject1.bin]`, `EmbeddedFiles[ObjectPool/_1234/EPRINT]` — using the same package-path value a readable item carries on [ydk:entity:extraction/SubfileItem], so the caller can line a field error up against the document's own structure. No number could serve: a failed item is absent from the returned list, so returned positions shift around the gap, and the only other number in play is the 1-based `<N>` the naming rule bakes into a readable item's generated `FileName`, which is that same list position. The returned list position is in fact the one numbering left in the result, and it is not a field path.

When a failing item's package path is unknown or empty — a legacy storage whose own name could not be recovered is the realistic case — it is reported at the bare collection path `EmbeddedFiles`, with no key. The same bare path covers a fault in the enumeration of the container's items itself: exactly one `EmbeddedFiles` entry is recorded for the whole fault, not one per item, because the items past the fault were never reached and nothing at all is known about them. Those items are simply absent from the returned list and are *not* individually reported. That is this rule's one accepted blind spot, stated plainly rather than papered over: a caller learns that the list is incomplete, but not by how much.

The collection is empty, never null, when every leaf was populated — the signal for a clean extraction is an empty collection, not a null one, so a caller never has to null-check before iterating. Entries come in population order: general metadata, then format metadata, then the flat text, then embedded items in the order the container enumerates them. There is at most one entry per distinct field path, because each leaf is populated exactly once. The bare `EmbeddedFiles` path is the single exception and may repeat: once per failing item whose package path could not be determined, plus at most once more for a mid-enumeration fault.

Two behaviors that were previously accidental become specified by this rule, and "silently" is exactly what the change removes. Flat-text extraction that fails must now return the empty string *and* a field-error entry, where it previously returned the empty string alone and was indistinguishable from a genuinely empty document. An unreadable embedded item must now be omitted *and* recorded, where the omission previously reached nobody but a log reader.

Batch extraction (ADR-007) is unaffected in shape and explicit in meaning: a file that produced only field errors is a batch success, carrying a populated result whose field-error collection is non-empty, never a batch item error. The batch wrapper's per-item error channel means "this file could not be extracted at all" and keeps exactly the fatal set above as its causes. A caller scanning a batch for problems therefore has to look in two places — item errors for files that failed, field errors for files that partially succeeded — and that is the point: the two are different outcomes and collapsing them loses the partial result.

## Extensibility & DI

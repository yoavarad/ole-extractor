# Library Tradeoffs — Office File MIME Detection & Extraction

Research date: 2026-08-18. Synthesized from four parallel findings docs in this directory:
[`documentformat.openxml.md`](./documentformat.openxml.md), [`npoi.md`](./npoi.md),
[`openmcdf.md`](./openmcdf.md), [`legacy-landscape-scan.md`](./legacy-landscape-scan.md).

These are honest tradeoff tables for a human decision, not a pre-baked recommendation. Each
table ends with an "if forced to pick today" lean, which is a lean, not a lock.

---

## Table 1: OOXML parsing/metadata/text/embeddings (docx/xlsx/pptx)

| Candidate | License | Maturity / activity | Fit for our use case | Known gaps | i18n / emoji handling |
|---|---|---|---|---|---|
| **DocumentFormat.OpenXml** (existing baseline) | MIT | v3.5.1 (2026-03-18); ~4.6k stars; commits landing daily; owned and actively developed by Microsoft under `dotnet` org; .NET 8 first-class target | Already integrated and working in this project for docx/xlsx/pptx metadata+text+embeddings. Strongly-typed, schema-validated Core/App/Custom property APIs are genuinely solved. Image/media parts enumerate cleanly with content-type + bytes. | No unified "give me all embedded objects" API (OLE objects show up as several structural shapes — raw bin part, embedded package part, or VML/drawing fallback with no clean path to the real payload, per open issue #644). No flat-text-extraction convenience API — requires hand-rolled per-part DOM walking, and naive `InnerText` concatenation loses paragraph/cell boundaries. No built-in recursion/cycle-safety for nested embeddings. Legacy doc/xls/ppt entirely out of scope (not this library's job). | XML/zip-based, so Unicode/RTL/CJK/emoji round-trip correctly by construction on read; no evidence of the SDK mangling surrogate pairs. One write-path gotcha (BOM-prefixed UTF-8 vs Office's BOM-less UTF-8) is irrelevant to a read-only extractor. |
| **NPOI (XWPF/XSSF/XSLF)** | Apache-2.0 source; **2.8.0+ binaries carry a paid "maintenance fee" EULA for orgs ≥$10k/year revenue** (self-compiling from source, or pinning pre-2.8.0, avoids it) | ~6.2k stars, active commits/releases, healthy backlog (~51 open issues) | Can read/write docx/xlsx/pptx as an alternative to OpenXml SDK; anecdotally higher-level/more convenient for common tasks ("give me this cell's value") than OpenXml SDK's literal object model. But this project already has a working OpenXml integration — there is no clear case to swap it out, and doing so would mean re-validating an already-solved problem. | Less spec-faithful for edge cases/advanced formatting per anecdotal comparisons (no maintained feature-parity matrix found). Would introduce a second, licensing-encumbered dependency for a capability already covered. | No OOXML-path-specific Unicode issues found, but a confirmed-and-fixed surrogate-pair/emoji bug existed on the streaming-write (SXSSF) path (NPOI 2.7.4 changelog, "Bug 61246") — evidence the port has had real astral-plane-character bugs, even if since fixed. |

**If forced to pick today:** keep **DocumentFormat.OpenXml** — it's already integrated, working, MIT-licensed with no licensing ambiguity, and actively maintained by Microsoft. NPOI's OOXML support would only be worth revisiting if we adopt NPOI anyway for legacy formats and want one unified object model — but that trade would mean accepting NPOI's licensing complication for a capability we don't currently need replaced. This is a lean for the human to confirm, not a locked choice.

## Table 2: Legacy OLE (doc/xls/ppt) parsing/metadata/text

| Candidate | License | Maturity / activity | Fit for our use case | Known gaps | i18n / emoji handling |
|---|---|---|---|---|---|
| **NPOI (HWPF/HSSF/HSLF)** | Apache-2.0 source; **2.8.0+ binaries require a paid monthly fee from revenue-generating orgs ≥$10k/year** (tiered $15–$99/mo, via GitHub Sponsors); avoidable by self-compiling from source or pinning to pre-2.8.0 (pure Apache-2.0, no future fixes) | ~6.2k stars, real release cadence, .NET 8 targeted since 2.7.6/2.8.0 | Only mainstream, actively-maintained pure-.NET library covering all three legacy formats in one dependency, no COM/Office-install interop needed. HSSF (xls) is mature and production-proven ("still the king of legacy Excel processing in .NET" per maintainer). HWPF (doc) is "moderately functional" but sparser error-checking. HSLF (ppt) is explicitly the least mature of the three (POI's own characterization, inherited by the port). No unified interface between legacy parsers and their OOXML counterparts (XWPF/XSSF/XSLF) — must build the doc-vs-docx abstraction ourselves either way. | **Licensing complication is the headline gap** — needs an explicit policy decision (pay the fee, pin to 2.7.x and forgo fixes, or self-compile). HWPF/HSLF have documented past bugs (multi-thread issue, load failures fixed in 2.3.0) and no first-party performance data for our read/extract workload (only skewed vendor benchmarks on unrelated formula-heavy write workloads). | No NPOI-specific RTL/Hebrew/Arabic issues found either way — an evidence gap, not a confirmation of correctness. Legacy binary formats use internal compressed(1-byte)/uncompressed(UTF-16LE) string-encoding switches; NPOI as a direct port should replicate Apache POI's handling, but this needs empirical verification against a real Hebrew/Arabic/Persian/CJK/emoji test corpus before relying on it — a confirmed-and-fixed surrogate-pair bug exists elsewhere in the codebase (write path), suggesting these bugs are real but not necessarily present on the legacy read path specifically. |
| **DocSharp (manfromarce/DocSharp)** — active fork of dead b2xtranslator | MIT (core); optional `DocSharp.Renderer` pulls in community-licensed QuestPDF, avoidable | Genuinely alive: release as recent as 2026-08-11, 643+ commits, targets .NET 8/9/10 | Converts doc/xls/ppt → OOXML, which could in theory let a single OOXML-based extraction pipeline (Table 1's library) handle both legacy and modern formats. | Architected as a format *converter*, not an extraction API — no common DOM, no unified metadata API. **Embedded-OLE-object extraction is an open TODO, not implemented.** Image extraction is limited/config-dependent. Self-described as a "hobby project" with no maintenance SLA. Not production-primary material today. | Not evaluated in depth (out of scope given the OLE-extraction gap makes it unusable for our core requirement as-is). |
| **Raw OpenMcdf + hand-rolled parsing** | MPL-2.0 | See Table 3 — OpenMcdf itself is healthy/active | Gives full control over exactly what's parsed, avoiding NPOI's licensing question entirely and avoiding pulling in a large POI-style dependency. But this means hand-writing binary-record parsers for WordDocument/Workbook/PowerPoint Document stream internals (text runs, formatting, compressed/uncompressed string switches, RTL bidi handling) essentially from scratch, referencing the MS-DOC/MS-XLS/MS-PPT binary format specs directly. | Substantial engineering lift and risk — reinventing years of format-quirk-handling that NPOI/POI already encode, with correctness (especially exotic-script correctness) unproven until built and tested. Realistically only worth it for a narrow subset (e.g. "just enough to pull flat text and OLE-embedded streams," not full format fidelity). | Entirely in our own hands — good (no third-party bug surface) and bad (no third-party testing/bugfix history to lean on either) in equal measure. |

**If forced to pick today:** **NPOI**, but only after resolving the licensing question explicitly — either self-compile from source (Apache-2.0, sidesteps the EULA per its own terms) or pin to the last pre-2.8.0 release. It remains the only mature, actively-maintained option that covers all three legacy formats without a from-scratch binary-parser build-out. Budget explicit test-corpus validation time for Hebrew/Arabic/Persian/CJK/emoji text extraction from real .doc/.ppt files given the evidence gap. DocSharp is worth bookmarking (re-check in 6–12 months) but is not viable today due to the missing OLE-extraction feature. This is a lean for the human to confirm — the licensing question in particular is a policy call, not a technical one.

## Table 3: Raw CFB introspection for mime-sniffing and generic subfile walking

| Candidate | License | Maturity / activity | Fit for our use case | Known gaps | i18n / emoji handling |
|---|---|---|---|---|---|
| **OpenMcdf** | MPL-2.0 (file-level copyleft only — safe in a proprietary product) | 388 stars but ~20.8M NuGet downloads and 83 dependent packages (incl. `MsgReader`, 9.2M downloads) — small-looking but genuinely battle-tested in production; last push the day before this research; v3.2.0 released 2026-07-30; monthly-to-bimonthly release cadence; CVE (infinite-loop DoS, CVE-2026-41511) found and patched within its own release cycle (fixed in 3.1.3) | Purpose-built exact fit: `RootStorage.Open(Stream)` works directly off a `MemoryStream` over our `byte[]`; `EnumerateEntries()` is a true directory-only read (no document-content parsing) — exactly the "check magic bytes, then look at top-level stream names" sniffing recipe the project needs. Recursive `OpenStorage`/`OpenStream` walk is trivial to write for embedded-object discovery; `CfbStream` is a plain `System.IO.Stream` so byte extraction is bytes-in-bytes-out with no format awareness required. `CLSID` is exposed on entries as a more robust embedded-object-type signal than name alone. | README explicitly states "limited error tolerance/recovery" — must wrap reads in try/catch and treat malformed CFB as a graceful-failure path (relevant since we'll process arbitrary user-uploaded files). **Must pin ≥3.1.3** to avoid the directory-cycle DoS CVE (current 3.2.0 is fine). No high-level "give me embedded OLE objects" helper — we own the name/CLSID convention table (`Ole10Native`, `\x01CompObj`, `Package`, etc.) ourselves; this is expected given OpenMcdf's deliberately generic scope. `OpenMcdf.Ole` (property-stream metadata) is explicitly experimental if we want legacy SummaryInformation metadata later. | CFB directory-entry names are UTF-16LE internally; OpenMcdf exposes them as plain `System.String` throughout its public API — no extra decode/encode work needed for Hebrew/Arabic/Persian/Russian/CJK/emoji in stream/storage names. (The fixed-ASCII top-level names we actually key sniffing off — "WordDocument", "Workbook", "PowerPoint Document" — are spec-mandated and never localized, so this mainly matters for custom-named nested embedded-object entries.) |
| **NPOI's POIFS layer** | Apache-2.0 source; same 2.8.0+ binary-fee EULA complication as Table 2 | Same maintenance signal as NPOI overall (~6.2k stars, active) | Also a usable, generic public API (`POIFSFileSystem`, `DirectoryEntry`, `DocumentEntry`) for walking an arbitrary CFB tree independent of the higher-level HWPF/HSSF/HSLF parsers — same stream-name-based sniffing approach is viable here too. If NPOI is already a dependency for Table 2's legacy parsing, POIFS is "free" (no extra library) for the sniffing job as well. | Bundled inside the larger NPOI package — pulling it in purely for CFB introspection (if NPOI weren't otherwise needed) means taking on the full NPOI dependency and its licensing question just for a directory-walk capability that a much smaller, purpose-built library (OpenMcdf) already provides more cleanly. No embedded-object-enumeration convenience API here either — same manual tree-walk requirement as OpenMcdf, just with Java-POI-derived naming conventions (`MBD########` dirs, `ObjectPool`, `\1Ole10Native`) as the reference. | No dedicated evidence found either way for POIFS's directory-entry-name Unicode handling specifically (as opposed to document *content* encoding, covered in Table 2) — an evidence gap rather than a known problem. |

**If forced to pick today:** **OpenMcdf** for the sniffing/generic-CFB-walk job specifically — it's smaller, purpose-fit, MPL-2.0 with no licensing ambiguity, has a real production track record via downstream consumers, and doesn't force taking on NPOI's licensing question just to read directory entries. Whether NPOI's POIFS is *also* used later is really a downstream consequence of the Table 2 decision (if NPOI is adopted for legacy parsing anyway, POIFS becomes an available-for-free alternative for some CFB tasks) rather than a reason to prefer it for sniffing on its own merits. This is a lean for the human to confirm.

## Cross-cutting note

The single biggest open question surfaced across all four docs is **NPOI's post-2.8.0 "Open Source Maintenance Fee" EULA** on precompiled binaries (Apache-2.0 source remains fully open; the fee applies only to consuming the published DLL/NuGet package if the consuming org's annual revenue is ≥$10,000). This directly intersects the project's stated "OSS-only, no commercial libraries" constraint and needs an explicit human decision before NPOI is adopted for either Table 2 (legacy parsing) or, indirectly, Table 3 (POIFS) — options are: pay the fee, self-compile from source under Apache-2.0, or pin to the last fee-free release (2.7.x) and accept forgoing future fixes.

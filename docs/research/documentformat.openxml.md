# DocumentFormat.OpenXml — Research Spike

Research date: 2026-08-18. All facts below verified against primary sources (GitHub repo, NuGet, official Microsoft Learn docs) on this date — see [Citations/links](#citationslinks).

## Library name

**DocumentFormat.OpenXml** (the "Open XML SDK" for .NET), published by Microsoft. Source: [github.com/dotnet/Open-XML-SDK](https://github.com/dotnet/Open-XML-SDK). NuGet package IDs relevant to us:

- [`DocumentFormat.OpenXml`](https://www.nuget.org/packages/DocumentFormat.OpenXml) — the core SDK (strongly-typed OOXML object model + packaging APIs). This is the one the project already depends on.
- `DocumentFormat.OpenXml.Framework` — split out in v3.x as the lower-level packaging/schema-validation layer the core package depends on (transitive dependency, not something we reference directly).

## License

**MIT**, confirmed both on the [NuGet package page](https://www.nuget.org/packages/DocumentFormat.OpenXml) (license expression: MIT) and via the GitHub repo metadata (`license.spdx_id = MIT`, checked via `gh api repos/dotnet/Open-XML-SDK`). No dual-licensing or commercial-tier gating — fully OSS, satisfies the project's OSS-only constraint.

## API surface relevant to our use case

- **Package open/detect:** `WordprocessingDocument.Open`, `SpreadsheetDocument.Open`, `PresentationDocument.Open` (each takes a `Stream` or path, `bool isEditable`). These are OOXML/zip-specific — they do **not** detect or open legacy OLE/CFB `.doc/.xls/.ppt`; that half of the MIME-detection requirement is out of scope for this library entirely and must come from elsewhere.
- **Core/App/Custom metadata:** `PackageProperties` (via `WordprocessingDocument.PackageProperties` etc.) exposes Dublin-Core-ish fields (Title, Creator, Subject, Keywords, Created, Modified, LastModifiedBy, …) reading `docProps/core.xml` directly — no manual XML parsing needed. Extended (app.xml) properties come from `ExtendedFilePropertiesPart` / `Application` element (company, app version, word/page counts), and custom properties from `CustomFilePropertiesPart` → `DocumentFormat.OpenXml.CustomProperties.Properties`. All three are strongly typed. ([API: CoreFilePropertiesPart](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.packaging.corefilepropertiespart?view=openxml-3.0.1), [CustomFilePropertiesPart](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.packaging.customfilepropertiespart?view=openxml-2.8.1), [How-to: retrieve app properties](https://learn.microsoft.com/en-us/office/open-xml/word/how-to-retrieve-application-property-values-from-a-word-processing-document))
- **Embedded objects (OLE):** exposed as generic parts — `EmbeddedObjectPart` (content type `application/vnd.openxmlformats-officedocument.oleObject`, raw `.bin`) and `EmbeddedPackagePart` (a whole embedded OOXML/other package, e.g. an embedded .xlsx inside a .docx). Reachable via `MainDocumentPart.EmbeddedObjectParts` / `EmbeddedPackageParts` (and the worksheet/slide-part equivalents for xlsx/pptx). **There is no unified "give me all embedded objects with their real file type/name" API** — you get raw parts and must resolve type/extension yourself from content type + the OLE object's fallback representation (`Vml.Office.OleObject`, drawing fallback images, `oleObject1.bin`, etc.). This is confirmed as a real usage gap in [GitHub issue #644 "How to parse embedded file (OLE object) in pptx/docx"](https://github.com/dotnet/Open-XML-SDK/issues/644): the SDK maintainers point users to a Stack Overflow answer, not an SDK method, and even that answer only covers one of several observed OLE shapes (some render as WMF fallback images with no structured way to get the "real" payload).
- **Inline media (images/audio/video):** cleaner story — `ImagePart`, and other `MediaDataPart`-derived types are enumerable per document part (`MainDocumentPart.ImageParts`, etc.) with `.GetStream()` giving raw bytes and `.ContentType` giving the MIME type directly. No filename is stored intrinsically (OOXML part URIs like `media/image1.png` are the closest thing) — filenames must be synthesized from the part URI/content type, not read verbatim from the package.
- **Flat text extraction:** no built-in "give me the plain text of this document" method. The documented pattern ([Mastering Text in Open XML WordprocessingML Documents](https://learn.microsoft.com/en-us/previous-versions/office/developer/office-2010/ff686712(v=office.14)), [How-to: search and replace text](https://learn.microsoft.com/en-us/office/open-xml/general/how-to-search-and-replace-text-in-a-document-part)) is to walk the DOM (`Descendants<Text>()` for Word, cell/shared-string walking for Excel, `Descendants<DocumentFormat.OpenXml.Drawing.Text>()` for PowerPoint) and concatenate `.Text`/`.InnerText`. `OpenXmlElement.InnerText` exists and works recursively but is naive: it does not insert paragraph/run boundaries, so text from adjacent runs/paragraphs runs together without whitespace unless you insert separators yourself. **This confirms the project's existing baseline is doing necessary, non-trivial manual work** — the SDK gives you a safe, typed tree to walk, not a text-extraction convenience API.
- **DOM vs SAX (streaming):** the SDK has two access modes documented directly by Microsoft: the typed DOM (`WordprocessingDocument`/`OpenXmlElement` tree) which loads a part fully into memory, and a lower-level SAX-style forward-only reader/writer (`OpenXmlReader`/`OpenXmlWriter`) for large parts. Per Microsoft's own guidance: "With very large documents, the SAX approach is better given that it is faster and can prevent Out of Memory exceptions... DOM requires loading entire Open XML parts into memory." ([How to: Copy a Worksheet Using SAX](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/how-to-copy-a-worksheet-with-sax), [Parsing and Reading Large Excel Files with the Open XML SDK](https://learn.microsoft.com/en-us/archive/blogs/brian_jones/parsing-and-reading-large-excel-files-with-the-open-xml-sdk)). For our metadata/text/embed-extraction use case the DOM API is the natural fit (we need typed access to properties and parts anyway), but very large worksheets could benefit from the SAX reader if memory becomes a problem.

## Strengths

- Native, first-class .NET 8 target; MIT-licensed; backed by Microsoft with real, continuous commit/release activity (confirms it's not a dead OSS dependency risk).
- Strongly-typed, schema-validated object model removes an entire class of "malformed XML I wrote by hand" bugs versus raw zip+XML parsing.
- Core/App/Custom property extraction is a genuinely solved problem — three typed parts, no manual XML.
- Inline media enumeration (images etc.) is straightforward: parts are enumerable, content type and bytes are both directly accessible.
- Package format detection between docx/xlsx/pptx variants is handled for you once you know which of the three `*Document.Open` classes to try (though *which* class to call is still your job — see gaps below).

## Weaknesses/gaps

- **Legacy binary formats are entirely out of scope.** `doc/xls/ppt` (OLE/CFB) are not zip/OOXML at all — this library cannot open, sniff, or extract from them. A separate library (e.g. OpenMcdf or similar CFB reader) is required for that half of the MIME-detection and extraction requirements; this was already assumed by the project brief but is worth stating explicitly since it's the single biggest capability gap for this project.
- **No content-sniffing/MIME-detection API at all.** The SDK expects the caller to already know (or guess and retry) which `*Document.Open` to call; it throws on mismatch rather than identifying the file type for you. It is a container/object-model library, not a format-detection library.
- **No flat-text-extraction convenience API.** As above, `InnerText`/`Descendants<Text>()` require hand-rolled per-part-type (Word/Excel/PowerPoint) walking logic, and naive concatenation loses paragraph/cell boundaries — the caller must insert separators to avoid words from different paragraphs/cells running together.
- **No unified embedded-object API.** Confirmed via [issue #644](https://github.com/dotnet/Open-XML-SDK/issues/644): OLE objects can show up as several different structural shapes (raw `EmbeddedObjectPart` bin, `EmbeddedPackagePart` for embedded OOXML packages, or a VML/drawing fallback image with no easily reachable "real" binary), and there is no single SDK call that enumerates "all embedded subfiles with type + name" — this must be hand-built and will need per-shape fallback logic, matching exactly the "first-layer embedded subfiles" requirement in the project brief.
- **Nested/recursive embeddings are entirely manual.** There is no recursive walk API. The documented pattern for an embedded package (e.g., an .xlsx embedded inside a .docx) is: get the `EmbeddedPackagePart`, call `.GetStream()`, copy to memory, then re-open that stream with `SpreadsheetDocument.Open()` as an independent package — i.e., you recurse yourself, one level at a time, re-invoking the whole open/traverse pipeline. Fine for "first-layer" extraction (matches the brief) but confirms there's no built-in depth-limiting or cycle-safety; that's on us to bound.
- **Macro-enabled variants (docm/xlsm/pptm) are structurally identical for our purposes but have one extra opaque part.** `Open()` and the whole part-enumeration/text/metadata API work identically across macro and non-macro variants — the only difference is an additional `VbaProjectPart` holding a raw, SDK-opaque `vbaProject.bin` binary (the SDK does not parse VBA source/p-code; it only lets you get/set/remove the part as bytes). Real-world friction around macro-enabled files in the tracker skews toward *round-tripping* problems — `ChangeDocumentType` failing to fully strip/carry `vbaProject.bin` references ([#618](https://github.com/dotnet/Open-XML-SDK/issues/618), [#1209](https://github.com/dotnet/Open-XML-SDK/issues/1209), [#2039](https://github.com/dotnet/Open-XML-SDK/pull/2039)) — which is a write-path concern, not directly ours as a read-only extractor, but signals the macro-file code paths get less scrutiny than the plain document paths.
- **Large-file memory behavior is a known pain point on the write path** ([#1951](https://github.com/dotnet/Open-XML-SDK/issues/1951) OutOfMemoryException writing large Excel files, [#807](https://github.com/dotnet/Open-XML-SDK/issues/807) large parts failing on .NET Core). Less directly relevant since we're a read-only extractor, but it reinforces that the DOM API keeps whole parts in memory — a very large embedded worksheet's XML part will be loaded in full unless the SAX reader is used deliberately.

## Unicode/RTL/emoji findings

- Because OOXML is XML/zip-based, Unicode text (Hebrew, Arabic, Persian, Russian, CJK, emoji) round-trips correctly by construction in the common case — XML is UTF-8/UTF-16 natively and the SDK deserializes through standard .NET XML APIs into `string`/`System.Char` sequences, so surrogate pairs for astral-plane characters (most emoji) are preserved the same way any .NET `string` preserves them; no evidence found of the SDK mangling surrogate pairs.
- **One real, confirmed encoding gotcha:** the SDK writes UTF-8 **with a BOM** by default when saving parts, which diverges from what Office itself produces (Office writes UTF-8 without BOM) — see [issue #1064 "Why office365 xlsx sheet utf8 encoding but openxmlsdk is utf8-withbom"](https://github.com/dotnet/Open-XML-SDK/issues/1064). A maintainer response confirms this was a deliberate change (some XML renderers had problems without a BOM) and that it is not currently configurable, though the maintainers said they'd accept a PR to make it configurable via `OpenSettings`. **This is a write-path issue** (affects re-saving/round-tripping files), so it does not directly threaten our read/extract-only pipeline, but it's worth flagging if any downstream step later re-serializes OOXML parts and diffs byte-for-byte against an Office-produced original.
- No open issues were found describing the SDK itself corrupting/mojibaking RTL or CJK *text content* on read — the risks in this area are more likely to come from any custom text-extraction/concatenation logic we write (e.g., not respecting bidi run boundaries when flattening text) than from the SDK's XML deserialization itself.
- A related but distinct bug ([#1874](https://github.com/dotnet/Open-XML-SDK/issues/1874) "Setting PackageProperties.Title with 0x0001 Unicode Characters Results in an Error") shows the SDK can throw on certain control/invalid XML characters when *writing* properties — again a write-path concern, but suggests input sanitization thinking is still evolving in the library (see also open PR [#2064](https://github.com/dotnet/Open-XML-SDK/pull/2064), "add opt-in XML character sanitization for package save"). Not something that should block extraction (reading a property that already exists in a file will just deserialize the same character faithfully), but worth keeping in mind if the pipeline ever needs to re-emit OOXML.
